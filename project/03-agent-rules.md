# 03. AI Agent 技能引導與防幻覺檢核規則

## 核心規範
- **鎖定語言**：`zh-TW`（所有會議逐字稿整理、摘要重點、待辦事項與討論紀錄統一使用繁體中文；業界標準技術專有名詞如 `REST API`, `JWT`, `SQL`, `PR`, `CI/CD`, `Docker`, `KPI`, `OKR` 等強制保留原生英文）。
- **領域檢核規則**：
  1. **免指令自然語言優先原則 (`Conversational-First`)**：AI Agent 嚴禁要求終端使用者記憶或輸入繁瑣的 `CLI` 指令來建立會議或產出摘要；只要使用者以自然語言提供會議素材、指定專案或提出問題，AI 必須主動完成資料夾建立、三檔產出與內容更新。
  2. **先說明理解與執行流程，並建立雙軌清單**：AI 在處理任何會議轉錄、整理或會後討論更新前，必須先向使用者說明「對本次會議需求的理解」與「執行流程」，並列出**有編號排序的工作清單（Ordered Work Checklist）**與**雙軌驗證清單（程式/格式驗證 + 業務邏輯驗證）**。
  3. **影音轉錄解耦與語者分離完整性原則 (`ASR-First & Speaker Diarization Rule`)**：面對 `.mp3`、`.mp4` 等音視訊檔案時，區分為「非 LLM 專用轉錄（本機 `Whisper` / `WhisperX` / 專用 `STT API` 或外部匯入之 `.srt` / `.vtt` / `.txt` 字幕初稿）」與「AI 後處理校正」兩階段。AI 嚴禁在未取得轉錄文字或工具輸出前憑空捏造音訊內容；若使用者僅放入 `.mp3` / `.mp4` 且尚未有文字初稿，AI 應先自動偵測並呼叫本機/外部轉錄工具產出初稿（若環境未安裝轉錄引擎，則清楚提示一鍵安裝指令或請使用者提供字幕初稿）。在產出 `01-transcript.md` 時，每一段發言都必須具備明確的發言者標籤（如 `**[00:02:15] 王經理 (PM)**：`）；若尚無法確認某位語者的真實姓名，AI 必須先以具辨識度的角色代號（如 `Speaker A (疑似技術主管)`）標註，並在整理完成後主動詢問使用者是否要一鍵替換為真實姓名。
  4. **三檔分離與職責邊界原則**：每次會議必須嚴格維持 `01-transcript.md`（純客觀逐字紀錄，不摻雜 AI 主觀推論）、`02-summary.md`（結構化摘要、討論重點與決議）、`03-todos-and-discussion.md`（行動待辦清單與會後延伸討論）三檔分離，並統一歸檔於 `meetings/<專案名稱>/<YYYY-MM-DD>_<會議名稱>/` 目錄下。
  5. **週期性跨場次連貫與歷史衝突主動提醒原則 (`Cross-Meeting Continuity & Conflict Alert Rule`)**：在同一專案資料夾下新增會議時，AI 必須主動檢視該專案 `index.md` 與過往會議的 `02-summary.md`、`03-todos-and-discussion.md`：
     - 將前次未完成之待辦事項列入本次會議的「前期進度追蹤」區塊，並於會議整理完畢後同步更新專案 `index.md`。
     - **跨期衝突自動偵測與提醒**：若發現本次會議的發言、決議、時程、預算數據、規格定義或負責人指派，與之前會議已記錄的內容存在矛盾或衝突（例如：推翻先前決議卻未明言、上線日期或金額前後不符），AI 必須在 `02-summary.md` 與 `03-todos-and-discussion.md` 中建立「⚡ 與歷次會議衝突提醒」區塊，並列明「本次會議內容（附本次 `#Lx-Ly`）」與「先前會議內容（附先前會議日期與 `#Lx-Ly`）」，同時在對話中主動提醒使用者確認該衝突屬於「正式決策變更」還是「會議口誤」。
  6. **會後討論明確標記原則**：使用者在會後與 AI 進行的延伸討論、方案推演或事後補充決議，必須明確記錄於 `03-todos-and-discussion.md` 的「會後延伸討論區（Post-Meeting Discussion）」，與會議當下發生的原始決議清楚區隔，避免混淆會議現場事實與會後補充。
  7. **極簡純淨目錄原則（Zero-Clutter Directory Rule）**：使用者的會議工作區根目錄與 `meetings/` 各層資料夾中，**嚴禁建立或散落 `skills/`、`rules/`、`AGENTS.md` 等多餘的系統資料夾與設定檔**（所有底層引導配置預設強制隱藏收納，即 `hideSkillsRules: true`）。資料夾內只允許存在與會議直接相關的專案目錄、日期目錄與三份標準會議文件。
  8. **重要多媒體同目錄保存與大檔保護原則（Co-located Media & Large File Safety）**：原始錄音與錄影檔屬於重要會議資產，必須保存在該場會議的日期目錄內（`meetings/<專案名稱>/<YYYY-MM-DD>_<會議名稱>/media/`），嚴禁於轉錄完成後自動刪除。當使用者新建會議並匯入媒體時，AI 必須支援「對話框直接拖入外部路徑自動複製歸位」、「丟入工作區根目錄或專案目錄由 AI 自動偵測搬移歸位」以及「先由 AI 建立日期與 `media/` 資料夾再放入檔案」三種免手動建目錄的匯入體驗，並在 `01-transcript.md` 頂部建立可點擊的相對路徑連結（如 `[原始會議錄影](./media/recording.mp4)`）、檔案大小與雜湊資訊；同時透過 `.gitignore`（或選用 `Git LFS`）避免大型二進位影音檔在 `git commit` 時卡死版控，兼顧「本機會議目錄 100% 完整保存影音」與「版控順暢安全」。
  9. **文件完稿後強制檢核規則（Post-Creation Document Inspection Rule）**：每當新會議的三份文件（`01-transcript.md`、`02-summary.md`、`03-todos-and-discussion.md`）與專案 `index.md` 建立或修訂完畢後，AI **必須強制執行完稿檢核規則（不可跳過）**，逐項檢查：
     - **(a) 結構與純淨度**：三份會議文件與專案 `index.md` 是否皆已到位？原始影音檔是否已收納於該場會議的 `media/` 子目錄？工作區與會議目錄是否無任何多餘外露的系統檔（該檢核規則本身亦收納於隱藏目錄中，不弄髒資料夾）？
     - **(b) 語者分離完整度**：`01-transcript.md` 是否每一段發言皆有時間戳記與語者標籤？是否還有尚未替換為真實姓名的代號（如 `Speaker A`）？
     - **(c) 摘要與待辦溯源真實性**：`02-summary.md` 與 `03-todos-and-discussion.md` 中的每一條重點、決議與待辦事項，是否皆包含指向 `./01-transcript.md#Lx-Ly` 的有效行號引用且內容無偏離？
     - **(d) 待辦欄位與跨期一致性**：待辦事項的負責人（Owner）與期限（Due Date）是否齊全（未知者是否已明確標註 `待確認 (TBD)`）？前期未完成待辦與本次新待辦是否已同步至 `meetings/<專案>/index.md`？
     - **(e) 零佔位符與無損格式**：確認無任何未填寫的雙大括號模板佔位符或語法破版，並於對話回覆末尾附上「✅ 完稿檢核報告」向使用者報告檢查結果與待確認事項。
  10. **零幻覺、三級可控風險與高不確定性主動告知原則（Zero-Hallucination, Controllable Risk & Uncertainty Escalation Rule）**：AI 在處理會議資料與產出任何文件時，必須將所有資訊進行**三級確定性與風險控管**，嚴禁自行腦補或隱藏不確定性：
     - **🟢 已驗證事實（Verified Fact）**：有明確的 `01-transcript.md#Lx-Ly` 與 `[HH:MM:SS]` 原音支撐且語意無歧義。
     - **🟡 可控風險推論（Controllable Inferred Risk）**：依前後文或專案背景合理推斷（例如依職責推論某位發言人或關聯影響），必須明確標註 `🟡 [上下文推論 - 建議確認]` 並主動說明推論依據與潛在風險。
     - **🔴 高不確定性需人為介入（High Uncertainty / Human Intervention Required）**：
       - **語者不確定**：多人重疊發言或上下文不足以判斷 `SPEAKER_XX` 是誰時，保留 `⚠️ [待確認語者: SPEAKER_XX]` 並提供時間戳記 `[HH:MM:SS]` 請使用者指認。
       - **關鍵字詞與數據不確定**：關鍵金額、時程、客戶名稱或技術名詞出現語意不通或疑似同音誤聽時，標註 `⚠️ [需人為確認原音 - HH:MM:SS]`，提示點擊 `./media/` 原始影音查驗。
       - **決議與待辦歸屬不確定**：正反意見拉鋸未拍板，或僅口頭提及無人正式承接時，嚴禁寫入正式決議或強派負責人，必須列入 `03-todos-and-discussion.md` 的「🚨 需人為介入與風險確認清單」並主動說明不確定性。
  11. **會後衍生文件與範本套用零幻覺規則（Post-Meeting Deliverable & Template Anti-Hallucination Rule）**：當使用者要求根據會議產出後續衍生文件（存放於當次會議目錄下的 `deliverables/`）時：
     - 若有指定或提供**範本（Template）**（如存放於 `meetings/<專案>/templates/` 或臨時傳入的範本），AI 必須嚴格維持範本的章節與欄位結構，僅填入本次（或歷次已驗證）會議有明確依據的內容並標註來源行號。
     - **範本缺漏欄位禁腦補鐵律**：若範本中有任何必填欄位（如「預算上限」、「驗收標準」、「法務條款」）在會議逐字稿中並未討論到，AI **絕對禁止自行編造內容填入**，必須在該欄位明確標記 `⚠️ [會議未提及 - 需人工補填]`，並在完稿檢核報告中主動列出所有缺漏欄位與風險提醒。
  12. **Token 成本最佳化與按需讀取原則（Token-Efficiency & Lazy-Loading Rule）**：為避免長會議與多場次累積導致 Token 消耗暴增，AI 必須嚴格遵守以下三項省 Token 鐵律：
     - **長篇逐字稿禁全文重寫 Output**：處理長篇轉錄初稿時，優先產出「語者代號（`SPEAKER_XX -> 實名`）與高頻同音錯字映射表」進行本機批次替換，不耗費大量 Output Token 逐字重印整份長文。
     - **跨期衝突比對僅讀 `index.md` 快照與前次摘要**：每次會議完稿後，必須將該專案「最新有效決議、關鍵時程/預算基準與未完成待辦」濃縮更新至 `meetings/<專案>/index.md`；下一場會議進行跨期衝突檢核時，**僅讀取 `index.md` 與前一場會議的 `02-summary.md` / `03-todos-and-discussion.md`，嚴禁遍歷讀取歷次會議的 `01-transcript.md`**。
     - **會後討論與衍生文件按行號局部讀取**：會後延伸討論或產出 `deliverables/` 文件時，預設僅讀取 `02-summary.md` 與 `03-todos-and-discussion.md`；若需核對逐字稿原話，僅依 `#Lx-Ly` 行號區間局部讀取 `01-transcript.md` 對應段落。
- **防幻覺驗收條件**：
  1. **100% 逐字稿來源溯源（Zero-Hallucination Citation）**：`02-summary.md` 中的每一項核心重點、決議事項，以及 `03-todos-and-discussion.md` 中由會議提煉出的每一項待辦（Action Item），都必須附上指向同目錄下 `[01-transcript.md](./01-transcript.md#Lx-Ly)` 的真實行號範圍引用；嚴禁憑空捏造逐字稿中未提及的決議、數據或承諾。
  2. **待辦事項指派防呆**：若逐字稿中僅提到「某件事需要做」，但未明確指定負責人或截止日期，AI 必須在待辦表格的負責人或期限欄位標註為 `待確認 (TBD)` 並列入「待釐清問題」，嚴禁自行猜測負責人或隨意編造截止日期。
  3. **零未填佔位符檢核**：所有產出之會議文件與專案規格文件不得殘留任何未替換的模板佔位符，且所有檔案路徑與行號連結皆須通過 0-Token `verify` 實體驗證。
